# Миграции базы данных

## Как это работает

Backend использует PostgreSQL и GORM. Версионированного каталога SQL-миграций, журнала версий и отдельной команды миграции сейчас нет:

- `backend/internal/models/models.go` — модели и GORM-теги полей, индексов и связей.
- `backend/internal/database/database.go` — `Migrate`, который вызывает `AutoMigrate` для `User`, `RefreshToken` и `Monitor`.
- `backend/cmd/server/main.go` — при каждом старте открывает соединение, вызывает `Migrate` и только после успешного завершения запускает HTTP-сервер. Ошибка миграции завершает процесс.
- `backend/internal/config/config.go` — настройки соединения; `DATABASE_URL` по умолчанию указывает на локальную БД `uptime` на порту 5432.
- `docker-compose.yml` — локальный PostgreSQL 16 и постоянный volume. Значения `POSTGRES_*` влияют на создание новой БД при инициализации volume.

`AutoMigrate` подходит для поддерживаемых GORM изменений схемы, но не является системой версионирования или отката. Не рассчитывайте, что удаление или переименование поля удалит либо переименует столбец или перенесёт данные: старый столбец может остаться, новый — появиться пустым. Изменения типов, `NOT NULL`, уникальности и связей могут завершиться ошибкой на существующих данных. Повторный запуск не заменяет проверку содержимого и ограничений.

## Порядок работы

1. Определите текущую и целевую схему, затронутые данные и совместимость старой и новой версии приложения. Изучите существующие модели, вызов `Migrate`, запросы и тесты, использующие изменяемые поля.
2. Для новой таблицы или поддерживаемого изменения обновите модель и её GORM-теги; новую модель добавьте в `AutoMigrate` в `backend/internal/database/database.go`. Обновите код, использующий схему. Для обязательных полей и уникальных индексов заранее учтите существующие строки и возможные дубликаты.
3. Если требуются перенос или преобразование данных, переименование, удаление, сложные ограничения или гарантированный порядок изменений, спланируйте явную миграцию и её безопасный повторный запуск. Не предполагайте, что `AutoMigrate` выполнит эти операции. В проекте пока нет принятого механизма таких миграций: сначала определите и реализуйте подход в рамках задачи, включая порядок относительно `AutoMigrate`, обработку ошибок и откат или восстановление. Не выполняйте необратимые SQL-команды на рабочих данных без согласованного плана.
4. Подготовьте резервную копию и проверьте возможность её восстановления перед изменением ценной базы. Для несовместимых изменений предусмотрите поэтапное развёртывание и обратную совместимость, а также способ восстановления данных и предыдущей версии приложения. Откат кода сам по себе не откатывает схему.
5. Проверьте как создание схемы с нуля, так и обновление базы со старой схемой и представительными данными. Включите случаи с `NULL`, дубликатами, связями и граничными значениями, если они относятся к изменению. Используйте только изолированную тестовую базу, не производственные данные.
6. Запустите миграцию повторно и проверьте идемпотентность: сервер стартует без ошибок, схема и данные не изменились неожиданным образом. При ошибке изучите логи и состояние базы: не предполагайте, что все изменения автоматически откатились.
7. Зафиксируйте в описании изменения действия при развёртывании, влияние на данные, план восстановления и результаты проверок. Если добавлен новый механизм миграций, обновите этот гайд.

## Локальная проверка на чистой базе

Ниже команды выполняются из корня репозитория. Они создают **отдельный временный** контейнер PostgreSQL и не используют volume Compose. Нужны Docker, Go и свободные порты 55432 и 18080. Если имя контейнера или порт уже заняты, выберите другие и согласованно измените команды. После удаления контейнера тестовые данные исчезнут.

```sh
docker run -d --name uptime-migration-test \
  -e POSTGRES_USER=uptime -e POSTGRES_PASSWORD=uptime -e POSTGRES_DB=uptime \
  -p 127.0.0.1:55432:5432 postgres:16-alpine
```

Дождитесь готовности (`accepting connections`):

```sh
docker exec uptime-migration-test pg_isready -U uptime -d uptime
```

Из каталога `backend/` запустите сервер с явным адресом тестовой базы:

```sh
DATABASE_URL='host=localhost user=uptime password=uptime dbname=uptime port=55432 sslmode=disable' \
HTTP_ADDR=127.0.0.1:18080 go run ./cmd/server
```

Сообщение `Server listening on 127.0.0.1:18080` означает, что вызов `Migrate` завершился без ошибки. Оставив сервер работающим, в другом терминале проверьте созданную схему:

```sh
docker exec -it uptime-migration-test psql -U uptime -d uptime
```

В `psql` используйте `\dt`, затем `\d users`, `\d refresh_tokens` и `\d monitors`. Сверьте столбцы, типы, nullable, значения по умолчанию, индексы и внешние ключи с моделями и ожидаемым результатом задачи. Для проверки данных выполните подходящие `SELECT`; выход — `\q`. Остановите сервер через Ctrl+C, запустите его с теми же переменными ещё раз и повторите проверку схемы и данных.

После проверки остановите сервер и удалите только созданный тестовый контейнер:

```sh
docker stop uptime-migration-test
docker rm uptime-migration-test
```

## Проверка обновления существующей базы

Используйте отдельную тестовую базу: сначала запустите предыдущую версию backend на пустой базе, заполните её представительными данными и сохраните результаты контрольных запросов. Затем остановите старый сервер, запустите новую версию с тем же `DATABASE_URL` и сравните схему и данные с ожидаемыми. Проверьте чтение и запись через затронутые сценарии приложения, затем повторите запуск. Для воспроизводимости запишите версии кода, подготовленные данные, запросы и результаты. Не используйте основной Compose volume как одноразовую тестовую базу и не удаляйте его для проверки.

Из `backend/` дополнительно выполните:

```sh
go build ./...
go test ./...
```

Эти команды проверяют сборку и существующие тесты, но сами по себе не доказывают корректность миграции PostgreSQL. Если конкретную проверку не удалось выполнить, укажите это и причину в результате работы.
